H1|2. Dự án là gì

N1|Meowdoku là game Sudoku theo chủ đề con mèo, port từ Godot sang Unity để làm bản portfolio (bản trình diễn năng lực cá nhân) trình diễn (không phải bản thương mại). Luồng chơi chính:

C|Startup (khởi động) -> Tutorial/Home (hướng dẫn/trang chủ) -> Main Game (chơi chính) -> Win/Fail/Revive (thắng/thua/chơi tiếp) -> Next/Home (màn kế/về trang chủ)

N1|Thông tin kỹ thuật cơ bản:
B|Thiết kế dọc (portrait - màn hình dọc), độ phân giải cơ sở 1080x1920 (có kiểm tra thêm cả 1080x2400), tối đa 60 FPS (khung hình/giây).
B|Unity Editor version: 6000.3.19f1 (Unity 6).
B|Render pipeline (chuỗi xử lý kết xuất hình ảnh): URP - Universal Render Pipeline, phiên bản 17.3.0.
B|UI (User Interface - giao diện người dùng): dùng UGUI (Unity UI cổ điển dạng GameObject/Canvas, package com.unity.ugui 2.0.0), không dùng UI Toolkit (bộ UI mới dạng UXML/USS).
B|Input (nhập liệu): Unity Input System (package mới, bản 1.19.0) - không dùng Input Manager cũ.
B|Animation/tween (hoạt ảnh/nội suy chuyển động): DOTween (thư viện của Demigiant), nằm tại Assets/Plugins/Demigiant/DOTween.
B|Test framework (bộ khung kiểm thử): Unity Test Framework (1.6.0) - có cả EditMode test (chạy trong Editor, không cần Play) và PlayMode test (chạy khi game đang chạy thật), dùng NUnit (thư viện viết unit test cho .NET).

H1|4. Kiến trúc hệ thống - cách hoạt động

H2|4.1 Khởi động app - AppBootstrap.cs (Core/UI/AppBootstrap.cs)

N1|Tương đương file launcher.gd của Godot. Chạy qua các phase (giai đoạn) tuần tự bằng enum (kiểu liệt kê giá trị cố định) AppStartupPhase: Idle -> RuntimeSetup -> Splash -> PlatformBoundary -> Prewarming (làm nóng trước, ví dụ tải sẵn asset) -> DataSyncBoundary -> SplashCompletion -> Routing (định tuyến sang màn tiếp theo) -> Complete. Nó inject (tiêm phụ thuộc - dependency injection) các dependency qua trường [SerializeField] (thuộc tính hiện trong Inspector Unity) (UIManager, LocalizationCatalog, AbConfigRuntime...) - không có Singleton (mẫu thiết kế chỉ có 1 instance toàn cục) tự tạo, mọi thứ do scene sở hữu và wiring (nối dây/gán tham chiếu) qua Inspector.

H2|4.2 UI - UIManager.cs (Core/UI/UIManager.cs)

N1|Đây là bộ quản lý UI theo kiểu cached (có bộ nhớ đệm), layered window manager (quản lý cửa sổ theo tầng lớp), port từ UIManager autoload (script tự nạp toàn cục) của Godot. Quản lý:
B|_cache: giữ lại window (màn hình/cửa sổ UI) đã tạo để tái dùng (không Instantiate - khởi tạo mới - lại mỗi lần mở).
B|_stacks theo UiLayer (Default/Popup/Notice/Modal/Tutorial/Loading) - mỗi layer (tầng) có z-order (thứ tự hiển thị trước/sau) riêng.
B|Input guard (chặn input không mong muốn), mask (lớp phủ làm tối màn hình khi popup mở), nút Back, prewarm bất đồng bộ (asynchronous - không chặn luồng chính).
B|Toàn bộ page (trang/màn hình) định danh bằng enum UiName (Splash, Home, Game, Bank, Tutorial, Setting...) trong file Core/UI/UIContracts.cs.

H2|4.3 Save/load - SaveStore.cs + GameStateService.cs + GameStateData.cs

B|GameStateData: model (mô hình) dữ liệu thuần (level hiện tại, streak - số ngày chơi liên tục, daily, session stats...) - giữ tên field snake_case (kiểu đặt tên có gạch dưới) gốc để dễ đối chiếu với Godot.
B|GameStateService: lớp nghiệp vụ (business logic) xử lý thay đổi trên GameStateData.
B|SaveStore: adapter (lớp chuyển đổi/kết nối) lưu file, mã hóa AES (thuật toán mã hóa đối xứng) + PBKDF2 (hàm dẫn xuất khóa từ mật khẩu, 100.000 vòng lặp), dual-slot A/B (2 file để chống hỏng khi ghi giữa chừng), có verify (kiểm tra tính hợp lệ) + retry (thử lại) load 3 lần, migrate (chuyển đổi định dạng) từ save cũ. Đây là điểm kỹ thuật khá "ngon" để show trong buổi phỏng vấn (an toàn dữ liệu, atomic write - ghi file đảm bảo toàn vẹn không bị dở dang).

H2|4.4 Logic Sudoku cốt lõi - QueendokuCore.cs (class BoardStateModel)

N1|Model bàn cờ thuần C#, không phụ thuộc MonoBehaviour: kiểm tra xung đột (conflict), hoàn thành (completion), quản lý trạng thái từng ô (enum CellStateType: EMPTY/CAT/MARK/ERROR/DRAFT_CROSS/DRAFT_CAT/LOCKED_MARK). Đây là "luật chơi" - validator (bộ kiểm tra tính hợp lệ) độc lập để dễ unit test (kiểm thử đơn vị).

H2|4.5 Sinh level - LevelGenerator.cs + LevelData.cs + LevelBankIO.cs + BankData.cs

B|LevelBankIO: đọc file JSON level từ Resources/Levels/, giải mã XOR (phép toán bit dùng để mã hóa/giải mã đơn giản) bằng key cố định rồi parse (phân tích cú pháp) bằng MiniJson (JSON parser tự viết, không dùng thư viện ngoài).
B|Đã có 5.411 level thường đã port, cộng thêm các loại bank khác (SP, LK, LK Modified, LK Style, GC).
B|LevelGenerator: sinh màu vùng (region color) theo thuật toán tô màu đồ thị (graph coloring - kỹ thuật đảm bảo các vùng liền kề không trùng màu), dựa vào độ degree (số cạnh nối vào 1 nút trong đồ thị) và seeded LCG (Linear Congruential Generator - bộ sinh số giả ngẫu nhiên có thể tái lập bằng seed cố định), đảm bảo 2 vùng kề không trùng màu.

H2|4.6 Gameplay loop - GameSession.cs + GameplayManager.cs

N1|GameSession là state machine (máy trạng thái) thuần: Loading -> Entering -> Playing -> ResolvingWrongGuess (xử lý khi đoán sai) -> Won/Failed -> Leaving. GameplayManager là MonoBehaviour đóng vai trò "nhạc trưởng", lắng nghe input, gọi vào GameSession, bắn ra event (sự kiện - GameTransitioned, GameplayFeedbackRequested...) để các Presenter (lớp trình bày UI) phản ứng - mô hình gần giống Model-View-Presenter (MVP - mẫu kiến trúc tách dữ liệu, giao diện và lớp điều phối).

H2|4.7 Input - BoardGestureRecognizer.cs và các class trong Gameplay/Input/

N1|Nhận diện tap (chạm), double-tap (chạm 2 lần), swipe-paint (kéo để đánh dấu nhiều ô liên tiếp) độc lập khỏi Unity Input System trực tiếp - tách logic thuần (BoardGestureRecognizer) khỏi lớp đọc input thực, nên test được bằng EditMode test mà không cần chạy PlayMode.

H2|4.8 A/B Config - AbConfigBase.cs (Core/Config/)

N1|Port từ hệ thống A/B test config (cấu hình thử nghiệm phân nhóm A/B để so sánh hiệu quả) của Godot. Class generic (lớp dùng kiểu dữ liệu tổng quát) AbConfigBase<T> chứa Key, DefaultValue (giá trị mặc định), Timing, có thể override (ghi đè) giá trị debug. Bản offline dùng default value có sẵn (không kết nối remote config - cấu hình từ xa - thực), có khoảng 89 class config kiểu này trong dự án.

H2|4.9 Daily/Streak/Award, Profile/Robot/Rank (Core/Daily, Core/Profile, Core/Robot, Core/Rank)

N1|Các hệ thống meta/social (điểm danh streak hàng ngày, thưởng, avatar/frame, bảng xếp hạng có đối thủ là robot AI mô phỏng để tạo cảm giác cạnh tranh) - đều port từ Godot, chạy offline hoàn toàn, không có server thực.

H2|4.10 Ads/IAP/Auth/Online (Core/Ads, Core/Online, Core/Platform)

N1|Dùng no-op provider (provider giả - implementation rỗng không thực sự làm gì) để giữ luồng chạy được mà không cần SDK (Software Development Kit - bộ công cụ phát triển)/backend (hệ thống server phía sau) thực, vì đây chỉ là bản portfolio offline, không phải bản thương mại. Nếu bị hỏi về bảo mật: dự án không có endpoint (điểm cuối API) mạng thực nào đang mở, mọi thứ về online/auth (authentication - xác thực) đều là stub (bản giả lập trống) an toàn.

B|UI layer/z-order: Godot dùng nhiều domain (miền/nhóm) sắp thứ tự riêng biệt theo CanvasItem layer, còn Unity Canvas override-sorting (ghi đè thứ tự hiển thị) dùng chung 1 domain toàn cục. Phải tự thiết kế hằng số RuntimeLayerStride (bước nhảy layer tính lúc chạy) để tránh việc mở lại một page Default có thể che khuất một Popup đang mở. Đây là ví dụ cụ thể, kỹ thuật, chứng minh hiểu sự khác biệt kiến trúc UI giữa hai engine, không phải chỉ copy-paste code.
B|Level bank mã hóa XOR + custom JSON parser (bộ phân tích JSON tự viết, MiniJson) - hiểu về bảo vệ asset cơ bản.
B|Input tách biệt logic khỏi Unity API để unit-test được gesture recognition (nhận diện cử chỉ chạm/vuốt) (tap/double-tap/swipe) mà không cần chạy PlayMode - thể hiện tư duy testability (khả năng kiểm thử) từ đầu.
B|A/B config với default value: kiến trúc cho phép chạy offline với giá trị mặc định nhưng vẫn sẵn sàng nối remote config sau này - separation of concerns (tách biệt trách nhiệm giữa các phần code) tốt.
B|Toàn bộ quá trình có roadmap ghi lại quyết định kỹ thuật (ví dụ: khi nào port 1:1, khi nào phải viết adapter riêng cho Unity) - đây là tài liệu có thể mở ra cho nhà tuyển dụng xem nếu họ hỏi sâu, chứng minh có quy trình làm việc rõ ràng chứ không làm tùy hứng.
B|Khả năng phối hợp với AI coding agent (Codex/Gemini) một cách có kiểm soát: phân công rõ vai trò (Gemini chỉ đọc và báo cáo, Codex mới được sửa code), tự review và quyết định khi nào một phần hoàn thành - đây là kỹ năng làm việc hiện đại, không phải "cheat" (gian lận).

H1|8. Phụ lục thuật ngữ (tra nhanh)

B|Port / Porting: chuyển đổi một phần mềm/game từ nền tảng hoặc engine này sang engine/nền tảng khác.
B|Engine: bộ khung phần mềm dùng để xây dựng game (ví dụ Unity, Godot).
B|Scene: một "cảnh" hoặc màn hình trong Unity, chứa tập hợp GameObject.
B|GameObject: đối tượng cơ bản trong Unity, là "vật thể" trong scene.
B|MonoBehaviour: lớp cơ sở của Unity mà mọi script gắn vào GameObject phải kế thừa.
B|Prefab: một "khuôn mẫu" GameObject đã đóng gói sẵn, có thể tái sử dụng nhiều nơi.
B|Namespace: cách gom nhóm code C# theo tên miền logic, tránh trùng tên class.
B|Enum: kiểu dữ liệu liệt kê các giá trị cố định (ví dụ: trạng thái Idle, Playing, Won).
B|Singleton: mẫu thiết kế chỉ cho phép tồn tại 1 instance (thực thể) duy nhất trong toàn chương trình.
B|Dependency Injection (DI): kỹ thuật "tiêm" các đối tượng phụ thuộc từ bên ngoài vào, thay vì tự tạo bên trong class.
B|SerializeField: thuộc tính C# trong Unity giúp field hiện ra và gán được trong Inspector.
B|Instantiate: hàm Unity dùng để tạo bản sao (clone) của Prefab hoặc GameObject lúc chạy.
B|Cache / Caching: lưu tạm dữ liệu/đối tượng đã tạo để dùng lại, tránh tạo lại nhiều lần gây tốn hiệu năng.
B|Z-order: thứ tự các lớp UI/vật thể hiển thị trước hay sau (cái nào che cái nào).
B|Async / Asynchronous: bất đồng bộ, tức là chạy song song không chặn (block) luồng chính của chương trình.
B|API: Application Programming Interface - giao diện lập trình ứng dụng, tập hợp hàm/lớp cho code khác gọi vào.
B|JSON: JavaScript Object Notation - định dạng dữ liệu dạng văn bản, dễ đọc, hay dùng để lưu cấu hình hoặc dữ liệu.
B|Parser / Parsing: bộ phân tích cú pháp, chuyển văn bản (như JSON) thành cấu trúc dữ liệu dùng được trong code.
B|Encryption / Mã hóa: biến đổi dữ liệu để người không có khóa (key) không đọc được nội dung gốc.

B|AES: Advanced Encryption Standard - một thuật toán mã hóa đối xứng phổ biến, an toàn.
B|PBKDF2: Password-Based Key Derivation Function 2 - hàm dùng để biến mật khẩu thành khóa mã hóa an toàn hơn (chạy nhiều vòng lặp để chống dò khóa).
B|Atomic write: cách ghi file đảm bảo file luôn ở trạng thái toàn vẹn (hoặc ghi xong hoàn chỉnh, hoặc không đổi gì), tránh hỏng file khi mất điện/crash giữa lúc ghi.
B|Unit test: kiểm thử một đơn vị code nhỏ (thường là 1 hàm/1 class) một cách độc lập.
B|EditMode test: loại test của Unity Test Framework chạy ngay trong Unity Editor, không cần bấm Play.
B|PlayMode test: loại test chạy trong lúc game đang ở trạng thái Play (mô phỏng runtime thực).
B|NUnit: thư viện viết và chạy unit test phổ biến cho .NET/C#, được Unity Test Framework dùng bên trong.
B|State machine (máy trạng thái): mô hình lập trình quản lý các trạng thái (state) và quy tắc chuyển đổi (transition) giữa chúng.
B|Event: sự kiện - cơ chế "bắn thông báo" khi có việc gì xảy ra, để các phần code khác lắng nghe và phản ứng.
B|MVP (Model-View-Presenter): mẫu kiến trúc tách dữ liệu (Model), giao diện (View) và lớp điều phối trung gian (Presenter).
B|Gesture recognition: nhận diện cử chỉ chạm/vuốt của người dùng (tap, swipe, double-tap...).
B|A/B testing: kỹ thuật thử nghiệm 2 (hoặc nhiều) phiên bản khác nhau trên các nhóm người dùng để so sánh hiệu quả.
B|Remote config: cấu hình lấy từ server ở xa, cho phép thay đổi hành vi app mà không cần cập nhật lại ứng dụng.
B|Stub / No-op: đoạn code giả, cài đặt (implementation) rỗng hoặc không làm gì thực chất, dùng để giữ luồng chạy khi chưa có hệ thống thực.
B|Backend: hệ thống phía server, xử lý dữ liệu/logic ở xa, khác với phần chạy trên máy người dùng (client).
B|Endpoint: một địa chỉ/API cụ thể mà client gọi tới để giao tiếp với server.
B|Graph coloring (tô màu đồ thị): thuật toán gán màu/nhãn cho các nút trong đồ thị sao cho 2 nút liền kề không trùng màu.
B|Seed / Seeded random: giá trị khởi tạo cho bộ sinh số ngẫu nhiên, giúp kết quả ngẫu nhiên có thể lặp lại được (deterministic).
B|Separation of concerns: nguyên tắc thiết kế tách các trách nhiệm khác nhau của code ra thành từng phần riêng biệt, dễ bảo trì.
B|QA (Quality Assurance): đảm bảo chất lượng - quy trình kiểm tra để phát hiện lỗi/vấn đề trước khi phát hành.
B|Smoke test: kiểm thử nhanh, cơ bản, để chắc bản build không bị lỗi nghiêm trọng ngay khi mở lên.
